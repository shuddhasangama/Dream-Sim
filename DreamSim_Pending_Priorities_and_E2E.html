What shipped in v3 — Segments G, H, I, J, and the nine UI points

  • All ten journey segments A–J now run end to end. The four remaining ceremonies are attached (contact share, home invite, relationship entry, stage gate), the ₹2,999 checkpoint fee is charged where the checkpoint actually happens, and the duplicate signature path inside /gate is gone.
  • The stage gate became a conversation, not a form. Each of you chooses what you want asked; Guru puts it to both of you unattributed; neither sees the other's words; and a 12-hour pause runs before anything can be committed — restarted every time a new question is asked. Nothing crosses between partners except through Guru.
  • Guru shows one answer, not nine tiles. A stage gate someone has raised is now the first thing on the screen and names who raised it. At most two cards sit under the answer; the rest are one link away at /guru/everything.
  • One post-date screen. Expectations, contact sharing and the next-level conversation were three separate invitations; they are three sections of /after-date now.
  • The eight requested changes are in — sign + face on the date agreement, the debrief opening an hour after the date, socials and feedback after the first date, the ₹999 late-cancellation charge, the five mandatory Stats, city-driven defaults, REACH honouring only keyed-in filters, and date-alignment fields collected when there is a date rather than at sign-up.
  • Schema drift can no longer ship. reconcile_columns() adds missing columns from the schema file on both backends at start-up — proved against a real PostgreSQL 16 built from yesterday's schema — so a deploy needs no manual ALTER and local and Railway cannot diverge.
  • Tests: 699 → 909 across 31 modules, verified on SQLite in-memory, SQLite on disk, and a real PostgreSQL server.

What changed under Segments G–J, and what it cost. The expensive part really was already done — the ceremony was one component and the milestone table already knew the ordering — so this was wiring, as expected. Three things were not:
  • Two gates disagreed with each other. disclosure.py opened contact sharing at the first date; escalations.unlocks_available() demanded two. Both were "the rule". The first date won, and the second rule was deleted rather than reconciled — two rules for one thing is how they drift.
  • Guru had no knowledge of the stage gate at all. It was a tile in a list of nine, which is why "one of them has raised the next stage" could be the ninth thing you saw. StageGate.raised_by is new; without it Guru cannot say the true sentence about who moved first.
  • Guru asked for a signature on a date that had already happened. Invisible while nine tiles competed for attention; the whole screen once there is one answer. Cutting the hub down is what surfaced it.

The three schema rules you set, and how each is now enforced.
  • All mixed-case PostgreSQL identifiers are consistently quoted. A static lint fails the build if any table, index or foreign key is declared unquoted, or if the two schema files disagree.
  • Foreign keys and indexes are checked along with table declarations. Same lint, same run — a table can no longer pass while its index quietly folds to lower case.

And the requirement underneath all three — “the updated code doesn't corrupt anything already done” — is what reconcile_columns() answers: it only ever adds. A column that would need NOT NULL without a default is reported and left alone, never guessed at.

PostgreSQL folds unquoted identifiers to lower case, so the app asked for "Account" and got relation does not exist. The two worth deciding before more building.
  • The matching model is too tight. Four viable pairs in a pool of 200 is not a data-seeding artefact — it is what the filter rules produce. Widening ranges, relaxing the distance model, or making REACH actively push people to widen are all product decisions, and every one of them changes what a user experiences on day one. Unchanged since v2, and now the oldest open item on the list.
  • Consent versioning. The bill clause is fixed, but the underlying problem is not: clauses are regenerated at render time, so nothing records what was actually signed. A document whose whole premise is "this is a readback of what you told us" needs to be able to show what it said on the day.
